## Scope and method

Reviewed `CartmanFatass/OpenResearch-hardened` at
[`57f880313c29ac2a290f78f7937aaaa018a1a033`](https://github.com/CartmanFatass/OpenResearch-hardened/tree/57f880313c29ac2a290f78f7937aaaa018a1a033).

The `security-hardening` branch was one commit behind initial `main`; no existing pull
request was present when this review began. Findings below distinguish the
reviewed baseline from the changes accompanying this report.

This is a targeted source and regression-test audit of feedback, untrusted
content, agent permission policy, credentials/remote launch, telemetry,

## Additional confirmed findings and changes

### 1. Plan-mode “read-only” approval can authorize writes or execution

**Priority: high when this classifier is relied on as an approval boundary.**

The baseline classified `sort` and `uniq` by program name with arbitrary
arguments. Both support writing named output files. Examples classified as
read-only included `sort -o /tmp/output /tmp/input` and
`echo data | uniq - /tmp/output`.

Whitespace-only tokenization also left shell quote removal unaccounted for:
`orx exp desc e-1 --s''et=changed` and `git log --out''put=/tmp/output`
hid write flags from the string checks. Attached Git flags such as
`git branch -uorigin/main` bypassed the exact-option denylist. Git read verbs
can execute configured helpers (for example fsmonitor/textconv/pagers), so a
short write-option denylist cannot establish the promised property.

The patch uses conservative tokenization, rejects shell expansions and
ambiguous syntax, removes arbitrary Git/sort/uniq auto-approval, and narrows
executable-path handling. Rejected commands defer to the harness's normal
approval policy. This can cause more approval prompts; it does not remove the
ability to run those commands after approval. Trusted executable resolution
and the actual harness/sandbox remain part of the boundary.

### 2. Kubernetes silently reuses stale credentials and shares mutable state

**Priority: high confidentiality risk on reused namespaces.**

`src/jobs/kubernetes.rs` previously applied the namespace-global `orx-env`
Secret only if the current environment was nonempty. Every primary Job
container nevertheless received an optional reference to that Secret.
Removing the last synced credential therefore left the old token available
to subsequent jobs. The same mutable Secret also allowed pending/concurrent
runs to pick up another run's later credential snapshot.

The patch creates an immutable, validated run-specific Secret, including an
empty map. A required reference is added to the script container only;
explicit legacy references in supplied manifests are rewritten to the
run-specific Secret. Existing custom sidecar references remain explicit user
configuration. The Secret is Job-owned for garbage collection and tracked
for failure rollback. New code does not overwrite/read the legacy global
Secret, but **does not delete historical Secrets or revoke already distributed
credentials**. Submissions now require permission to create/delete per-run
Secrets even for an empty snapshot; manifests must not define the reserved
managed Secret themselves. Remove historical `orx-env` resources only after checking older
active jobs; rotate exposed credentials separately if necessary.

### 3. Per-run telemetry opt-out does not cover consent

**Priority: medium; public-path reachability requires a telemetry-eligible build.**

`record_consent(true)` could ignore both `ORX_NO_TELEMETRY` and
`--no-telemetry`; consent retries intentionally bypassed the persisted
preference and accidentally bypassed per-run choices too. A regression test
with a local HTTP listener observed the unwanted POST before the fix.

A shared per-run gate now guards consent creation, queue traversal and final
queued delivery. Production eligibility is unchanged. Fork source builds
already stopped public telemetry entry points; this was a latent eligible-
build bug, not evidence that current fork source builds were transmitting.

### 4. SSH TOFU does not fail closed when the pin store cannot be used

**Priority: high under a broken or hostile pin-store configuration.**

The baseline `ensure_known_hosts_dir` checked only parent-directory creation.
OpenSSH `accept-new` can authenticate even when writing the newly observed
key fails; `LogLevel=ERROR` can hide the warning. An isolated local sshd
reproduction accepted two successive different server keys at one address
when the configured known_hosts path was a directory.

A second isolated sshd reproduction found that a raw known_hosts pathname
containing spaces was split by OpenSSH into different paths; two successive
keys were accepted while the intended file stayed empty. Path expansion and
option parsing must match the path checked by the application.

The patch validates a regular, non-symlink, writable owner-controlled private
pin file before starting the provisioned-host SSH path, and serializes its
literal path for OpenSSH rather than reconstructing it from the option string. It does not alter
user SSH-config aliases. This closes the reproduced unusable-store condition;
preflight alone cannot guarantee durability after disk exhaustion, defend
against another process with write authority over an ancestor directory changing the path, or
verify the very first server identity out of band. This remains TOFU, not a
provider-certified host-key pin.

### 5. Installation/update can silently lose all fork hardening

**Priority: high integrity/configuration risk; no upstream compromise needed.**

The baseline README recommended the upstream install script and desktop
binaries. `src/updates.rs::REPO_URL`, platform install hints and Cargo's
repository metadata also pointed upstream. An ordinary install or later
manual/opted-in update could replace the hardened fork with upstream code.

The patch makes update sources and installer hints derive from this fork's
Cargo repository identity, and adds identity regression tests. The README
now gives source-build instructions and explicitly labels inherited upstream
packaging documentation. Missing fork assets fail closed; there is no upstream
fallback. The upstream-only official-build and signing workflow is not
expanded here. Compatible fork releases still require maintainer work.

### 6. Secret files are initially created with ambient permissions

**Priority: medium on multi-user machines with permissive umask.**

`save_credentials` and `save_overleaf_credentials` wrote bytes before applying
0600. That allows a transient readable inode (often 0644) and follows an
existing symlink. Rewriting an existing overly broad synced-env file also
wrote new values before chmod.

The patch reuses the existing create-new, owner-only temporary-file writer
and atomically renames the completed inode. It rejects destination symlinks;
new values are not written through a pre-existing hard link. Regression tests
check private final permissions, unchanged old hard-link data, symlink refusal
and temporary-file cleanup. Windows retains inherited directory ACL semantics;
this is not a claim to implement a new Windows ACL policy.

### 7. Feedback skip looks like successful delivery

**Priority: low correctness/transparency issue.**

A telemetry-ineligible feedback command returned success without output.
An agent could tell the user a report had been sent when it had been skipped.
The command now explicitly reports “not sent” on the disabled path and prints
submission confirmation only after a successful service response. This is
observability, not proof of per-report authorization.

### 8. Paper metadata falls outside the untrusted-content frame

**Priority: defense-in-depth gap in the prompt boundary.**

The baseline framed abstract/body text but printed titles, authors, journal,
category and repository links first. With no abstract, some results had no
warning at all. Remote metadata can contain instructions just like body text.
The patch renders the complete successful result through one framing helper,
escapes reserved marker strings and terminal control characters, and adds
malicious metadata/body fixtures for all four literature sources. This makes
the intended boundary explicit and prevents trivial textual marker collisions;
it does not make arbitrary model behavior safe. Other tool/error output paths
still need to be treated as untrusted by the consuming agent.

## Important residual risks / non-goals

- Default autonomous permissions are unchanged. Plan-mode classifier fixes do
  not make Auto/Bypass or all providers safe for hostile papers.
- Prompt wrappers and the consent language in skills are advisory. No test
  establishes that a model cannot be induced to ignore them. The PR does not
  present a model-supplied confirmation flag as human approval.
- Explicitly synced credentials remain globally scoped, including values
  saved by provider-specific forms. Destination-scoped secret stores and
  consent UI need a separate compatibility/migration design.
- GitHub asset digests share the release authority. A compromised release
  publisher can replace both content and metadata. Windows staged binary
  verification, remote bootstrap verification and independent release signing
  remain future work. Linux AppImage checksum and macOS signature/notarization
  checks already present were not removed.
- The update banner still links to upstream release notes; it is informational,
  not the download source. Changing it requires rebuilding the committed UI.
- The inherited source-build production-telemetry restriction and macOS
  upstream signing identity remain intact. Fork release packaging is not
  validated by this PR.
- No live Kubernetes/Modal/Slurm/Ray/cloud provider execution was performed.
  No dependency-wide audit, fuzz campaign or exhaustive malicious-prompt
  robustness evaluation was performed.
